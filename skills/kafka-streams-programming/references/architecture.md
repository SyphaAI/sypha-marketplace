# Kafka Streams Architecture

Internal mechanics of Kafka Streams. Consult this when explaining KS to users, sizing applications, or diagnosing issues.

**Docs:** [Architecture guide](https://docs.confluent.io/platform/current/streams/architecture.md)

## Core Concepts

Kafka Streams is a **client library** — it executes within your JVM process rather than on a dedicated cluster. Each instance connects to Kafka as a consumer, handles records, and writes results back to Kafka.

### Threading Model

```
KafkaStreams instance
├── StreamThread-1 (a Java thread)
│   ├── Consumer (polls from assigned partitions)
│   ├── Task 0_0 (partition 0 of subtopology 0)
│   │   ├── Processor topology
│   │   └── State stores (RocksDB)
│   ├── Task 0_1 (partition 1 of subtopology 0)
│   └── Producer (writes to output/changelog topics)
├── StreamThread-2
│   └── ...
├── GlobalStreamThread (if GlobalKTable is used)
│   └── Reads ALL partitions of global topics
└── StateRestoreThread
    └── Replays changelogs to rebuild state stores
```

- **StreamThread:** Each thread executes an event loop: poll → process → commit. A single thread can manage multiple tasks.
- **Task:** The fundamental unit of parallelism. One task is created per input partition per subtopology, and each task owns its associated state stores.
- **Subtopology:** A self-contained processing graph with no shared state. KS generates distinct subtopologies for disconnected sections of the topology.
- **GlobalStreamThread:** A dedicated thread for GlobalKTable — it reads all partitions and maintains a local replica of the complete table.

### How Partitions Map to Tasks

```
Input topic: orders (6 partitions)
Topology: orders → groupByKey → aggregate → output

Tasks created: 6 (one per partition)
If 2 instances with 1 thread each: 3 tasks per instance
If 1 instance with 3 threads: 2 tasks per thread
```

**Maximum parallelism equals the number of input partitions.** Having more instances or threads than partitions results in idle capacity.

### State Stores

Each stateful task has its own state store instance, backed by RocksDB by default. State characteristics:
- **Partitioned:** Task 0_0 holds state exclusively for partition 0's keys
- **Persistent:** Survives restarts through local RocksDB files
- **Recoverable:** Backed by changelog topics in Kafka — can be fully rebuilt from scratch
- **Off-heap:** RocksDB memory (block cache, write buffers) falls outside JVM heap control

### Lifecycle States

CREATED → REBALANCING → RUNNING → PENDING_SHUTDOWN → NOT_RUNNING (normal path)
RUNNING → PENDING_ERROR → ERROR (error path)

States: CREATED (not yet started), REBALANCING (task assignment in progress), RUNNING (actively processing), PENDING_SHUTDOWN (draining), NOT_RUNNING (clean exit), ERROR (unrecoverable failure).

### Commit and Flush

Commit cycle (`commit.interval.ms`): (1) flush state stores, (2) flush producer, (3) commit offsets.
- At-least-once: asynchronous, 30s default
- Exactly-once: transactional (atomic), 100ms default

**Cache** (`statestore.cache.max.bytes`): Sits in front of RocksDB. Collapses multiple updates to the same key within a commit interval. With 50MB cache and 30s commits, downstream consumers observe only the most recent value per key per cycle.

### Changelog Topics

Every state store has a dedicated changelog: `<application.id>-<store-name>-changelog`
- Non-windowed: `cleanup.policy=compact`
- Windowed: `cleanup.policy=compact,delete`

Recovery is achieved by replaying the changelog. Standby replicas remain warm by continuously replaying it.

### Repartition Topics

Generated by `selectKey()`, `groupBy()`, and `map()` when the record key changes. Naming convention: `<application.id>-<operator-name>-repartition`. **Retention is infinite** — DO NOT configure a retention period (doing so causes data loss).

### GlobalKTable vs KTable

| Aspect | KTable | GlobalKTable |
|--------|--------|-------------|
| Distribution | Partitioned | Replicated to all |
| Co-partitioning for joins | Required | Not required |
| Join key | Must match table key | Any field |
| Memory | Per partition | Full table per instance |
| Changelog | Yes | No (reads source) |

Use GlobalKTable when: the lookup dataset is small (under a few GB), the join key differs from the record key, or co-partitioning is impractical.

## Sizing Guidelines

### Parallelism

`total_threads = instances × num.stream.threads ≤ input_partitions`

Threads exceeding partition count are idle (hot standbys). For multi-subtopology apps, run `topology.describe()` to determine the real task count.

**Sizing guidance:**
- Stateless: increase threads per instance to match CPU, reduce number of instances
- Stateful: reduce threads per instance and size containers for RocksDB. Fewer large instances are preferable to many small ones — state restoration is costly.

### Memory (stateful apps) — canonical reference

Other files cross-reference this section for the RocksDB memory formula.

```
JVM heap: application objects + serde buffers + cache
  - statestore.cache.max.bytes is on-heap (divided among threads)
  - Typical: 512MB - 2GB heap

RocksDB off-heap: per state store instance
  - block_cache(50MB) + write_buffers(16MB × 3) = 98MB per instance
  - Non-windowed: store_instances = partitions_per_instance × stores
  - Windowed: store_instances = partitions_per_instance × stores × 3 (segments)
  - Typical: 1-10 GB off-heap

Container total = heap + off-heap + OS overhead (~256MB)
Set MaxRAMPercentage=75 to leave room for RocksDB
```

**Worked example (windowed aggregation):**
- 40 partitions, 1 windowed store, 4 instances → 10 partitions/instance
- Windowed segments: 10 × 1 × 3 = 30 store instances per app
- RocksDB memory: 30 × 98MB = ~2.9 GB off-heap
- Container: 2GB heap + 2.9GB RocksDB + 256MB OS = ~5.2 GB minimum

**BoundedMemoryRocksDBConfig:** For applications with many stores, configure a shared block cache across all RocksDB instances to cap total off-heap consumption. See `config-baseline.md` § Performance Tuning.

### Disk (stateful apps)

```
RocksDB disk = state_size × 3 (SST files + WAL + compaction overhead)
Standby replicas double the disk requirement
Use fast local storage (SSD), never NFS/EBS
Monitor disk usage with alerts at 70%
```

The 3x multiplier covers: active SST files, the write-ahead log, and temporary files generated during compaction. Windowed stores produce multiple segments per partition, adding to disk requirements.

**Always use persistent volumes (PVCs) in Kubernetes for stateful apps.** Ephemeral storage triggers a full state restoration on every pod restart, which can take hours for large state stores.

### Network and Broker Sizing

```
Stateless broker overhead:  ~1x input volume (read + write output)
Stateful broker overhead:   ~1.5-2x input volume (+ changelog writes)
EOS broker overhead:        ~2x input volume (+ transaction markers)
```

Changelog topics are replicated according to `replication.factor` (default 3). Each state store produces one changelog topic. Repartition topics contribute additional broker load roughly proportional to the original topic being remapped.

### Scaling

**Scale out** (add instances): Appropriate for network- or memory-bound applications. Tasks are redistributed following the rebalance.
**Scale up** (add threads/resources): Appropriate for CPU-bound applications. Requires increasing `num.stream.threads` and adjusting heap and RocksDB limits accordingly.
